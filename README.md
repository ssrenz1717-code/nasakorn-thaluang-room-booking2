# ระบบจองห้องประชุมและ Dashboard

> **สถานะ: MVP อยู่ระหว่างพัฒนา** — ดูห้อง/จอง/ยกเลิกได้แล้ว; ก่อนใช้จริงต้อง deploy และตรวจบนบัญชี Google ของเจ้าของระบบ

## สถาปัตยกรรมที่เลือก

| ส่วน | เทคโนโลยี | เหตุผล |
|---|---|---|
| ฐานข้อมูล | **Google Sheets** | ฟรี ไม่ต้องผูกบัตรเครดิต เปิดดู/แก้ข้อมูลเองได้ทุกเมื่อ |
| Backend | **Google Apps Script** | เป็นที่เดียวที่เขียนข้อมูลได้ — ทุกคำขอผ่าน `LockService.getScriptLock()` |
| Frontend | React 19 + TypeScript + Vite + Tailwind CSS v4 | ตามสเปก |
| Domain logic | TypeScript ใน `shared/` ไม่พึ่ง dependency ใด ๆ | bundle ไปรันบน Apps Script ได้ → หน้าเว็บกับ server ใช้โค้ดกฎธุรกิจ **ตัวเดียวกันจริง ๆ** |

### กันจองซ้ำได้อย่างไร

Google Sheets ไม่มี transaction และไม่มี constraint แบบฐานข้อมูลจริง แต่ Apps Script มี
[`LockService.getScriptLock()`](https://developers.google.com/apps-script/reference/lock/lock-service)
ที่เอกสารระบุว่าโค้ดในบล็อกที่ถูกล็อก *"cannot be executed simultaneously regardless of the identity of the user"*

ทุกคำขอจองจึงวิ่งผ่านประตูเดียวทีละคน: **ล็อก → อ่านการจองของห้องนั้นวันนั้น → ตรวจทับซ้อน → เขียน → ปล่อยล็อก**
ถ้า 20 คนกดจองห้องเดียวเวลาเดียวพร้อมกัน จะสำเร็จคนเดียว ที่เหลือได้ข้อความว่าไม่ว่างพร้อมเวลาว่างที่ใกล้ที่สุดให้เลือก

### ข้อจำกัดที่ต้องรู้ก่อนใช้ (ไม่ใช่ข้อเสียที่ซ่อนไว้)

1. **ไม่ใช่ real-time จริง** — Sheets ไม่มี push notification หน้าเว็บจึงถาม server ทุก 15 วินาที
   หน้าจอจะเขียนว่า "อัปเดตล่าสุด HH:mm:ss" ไม่เขียนคำว่า real-time
2. **ห้ามแชร์ไฟล์ Sheet ให้พนักงาน** — ถ้าแชร์ ใครก็แก้ข้อมูลตรง ๆ ได้ ข้ามทุกการตรวจสอบและทุกสิทธิ์ที่เราเขียน
   ไฟล์ต้องอยู่กับบัญชีผู้ดูแลคนเดียว พนักงานเข้าได้ทางหน้าเว็บทางเดียว
3. **เพดานการใช้งานพร้อมกันคือ 30 คำขอ** ([โควตา Apps Script](https://developers.google.com/apps-script/guides/services/quotas))
   พอสำหรับองค์กรหลักร้อยคน แต่ไม่ใช่ระบบที่รองรับคนหลายพันคนกดพร้อมกัน
4. **ความเร็วต่อคำขอ ~0.5-2 วินาที** ช้ากว่าฐานข้อมูลจริงอย่างเห็นได้ชัด หน้าเว็บจึงต้องมี loading state ทุกจุด
5. **อีเมลแจ้งเตือนจำกัด 100 ฉบับ/วัน** (บัญชี gmail.com) หรือ 1,500 ฉบับ/วัน (Google Workspace)
6. ถ้าโตเกิน ~50,000 รายการจอง ควรย้ายไปฐานข้อมูลจริง — โค้ดใน `shared/` ย้ายตามไปได้ทั้งหมดโดยไม่ต้องเขียนใหม่

## สิ่งที่ยังทำไม่ได้ตอนนี้ (ตามจริง)

- **ยังไม่พร้อมเปิดใช้จริง** — ต้อง deploy Apps Script, ตั้งค่า OAuth และตรวจระบบกับ Google Sheets จริง
- **ยังไม่ได้รันบน Apps Script จริงแม้ครั้งเดียว** เพราะต้องใช้บัญชี Google ของคุณ
  สิ่งที่ยืนยันแล้วคือ: เทส 115 ข้อผ่าน, bundle รันได้ในสภาพแวดล้อมที่ไม่มี module system,
  ทุก `Domain.xxx` ที่ฝั่ง Apps Script เรียกมีอยู่จริง, ทุกไฟล์ `.gs` syntax ถูกต้องตาม ES2019
  ส่วนที่ยืนยันไม่ได้จากเครื่องนี้คือ SpreadsheetApp / LockService / UrlFetchApp ของจริง
  → `runSelfTest()` ใน Apps Script คือตัวปิดช่องว่างนี้ (12 ข้อตรวจ)
- ยังไม่มี: เพิ่ม/แก้ไขห้อง, แจ้งเตือน, รายงานกรองและ CSV, จัดการผู้ใช้และตั้งค่าผ่านเว็บ (ส่วนที่เหลือของ M2, M5-M7)

## API ที่ใช้ได้แล้ว

| คำสั่ง | ต้องล็อกอิน | คืนค่า |
|---|---|---|
| `GET ?action=version` | ไม่ | `dataVersion` สำหรับให้หน้าเว็บถามว่ามีอะไรเปลี่ยน |
| `POST ping` | ไม่ | ตรวจว่า server ตอบ |
| `POST login` | ไม่ | ตรวจ Google ID token → คืน session token + ข้อมูลผู้ใช้ |
| `POST me` | ใช่ | ข้อมูลผู้ใช้ปัจจุบัน (อ่านสิทธิ์จากชีตสด ๆ) |
| `POST bootstrap` | ใช่ | ผู้ใช้ + ค่าตั้งค่าระบบ + dataVersion สำหรับโหลดหน้าแรก |
| `POST rooms` | ใช่ | รายการห้องประชุม |
| `POST bookings` | ใช่ | รายการจอง (พนักงานเห็นของตัวเอง; ผู้ดูแลเห็นทั้งหมด) |
| `POST createBooking` | ใช่ | สร้างรายการโดยตรวจเงื่อนไขและเวลาชนภายใน Script Lock |
| `POST cancelBooking` | ใช่ | ยกเลิกรายการตามสิทธิ์และนโยบายเวลาของระบบ |
| `POST decideBooking` | ผู้ดูแล | อนุมัติหรือปฏิเสธคำขอที่รอพิจารณา |

## หน้าเว็บ

```bash
cd web
npm install
npm run dev      # เปิดที่ http://localhost:5173
npm run verify   # typecheck + เทส 8 ข้อ (เปิดเว็บ เข้าสู่ระบบ ถึงหน้าภาพรวม สิทธิ์พนักงาน)
npm run build    # ได้ไฟล์พร้อมเผยแพร่ใน web/dist
```

**ใช้งานได้โดยไม่ต้องมีเซิร์ฟเวอร์** — ถ้ายังไม่ได้ตั้ง `VITE_API_URL` และ `VITE_GOOGLE_CLIENT_ID`
หน้าเว็บจะเข้าระบบในฐานะผู้ดูแลให้ทันที และเก็บการจองไว้ใน localStorage ของเบราว์เซอร์
(รีเฟรชแล้วไม่หาย แต่**แต่ละเครื่องเห็นข้อมูลของตัวเอง** ไม่ได้แชร์กัน)
ระบบยังใช้กฎการจองและตรรกะเวลาตัวเดียวกับที่ server ใช้ทุกอย่าง
เมื่อ deploy Apps Script และตั้งสองค่านั้นแล้ว จะเปลี่ยนไปใช้ Google Sheets ที่ทุกคนเห็นข้อมูลชุดเดียวกัน

เผยแพร่ขึ้น GitHub Pages อัตโนมัติผ่าน `.github/workflows/deploy-pages.yml`
(ตรวจ type + เทสทั้งสองฝั่ง + ตรวจว่า `Domain.gs` ตรงกับ `shared/` ก่อนจึงเผยแพร่)
ดูขั้นตอนใน `docs/02-เผยแพร่ขึ้น-GitHub-Pages.md`

## โครงสร้าง

```
web/                         # หน้าเว็บ React 19 + TypeScript + Vite + Tailwind v4
├── src/app/                 #   router, สถานะระดับแอป, เมนู
├── src/components/ui/       #   ปุ่ม การ์ด ป้าย แจ้งเตือน สถานะโหลด/ว่าง/ผิดพลาด
├── src/components/layout/   #   Sidebar, Topbar, โครงหน้า, เมนูโปรไฟล์
├── src/features/            #   auth (หน้าเข้าสู่ระบบ), dashboard (หน้าภาพรวม)
└── src/lib/                 #   API client, ที่เก็บข้อมูลในเบราว์เซอร์, จัดรูปแบบวันที่ไทย พ.ศ.
shared/                      # ใช้ร่วมกันระหว่างหน้าเว็บและ Apps Script
├── time/bangkok.ts          #   แปลงเวลาไทยทั้งหมดผ่านไฟล์นี้ที่เดียว
├── validate/check.ts        #   ตรวจรูปร่างข้อมูล ไม่พึ่ง dependency
├── domain/
│   ├── overlap.ts           #   ตรวจช่วงเวลาทับซ้อน + เสนอเวลาว่างแทน
│   ├── status.ts            #   สถานะการจองและกฎการเปลี่ยนสถานะ
│   ├── booking-rules.ts     #   กฎการตรวจคำขอจอง
│   └── utilization.ts       #   สูตรอัตราการใช้ห้อง
├── schemas/                 #   ชนิดข้อมูล + ตัวตรวจของแต่ละ entity
└── __tests__/               #   69 เทส
apps-script/
└── Domain.gs                # ผลลัพธ์ bundle (41 KB) สร้างด้วย npm run build:domain
```

**กฎเหล็ก 3 ข้อ** — มีเทสบังคับทุกข้อ ไม่ใช่เขียนเตือนไว้แล้วหวังว่าจะมีคนอ่าน:
1. `shared/` ห้าม import dependency ภายนอกแม้แต่ตัวเดียว (`shared-deps.test.ts`)
2. bundle ต้องไม่มี `require` / `process` / `import()` และรันได้โดยไม่มี module system (`appsscript-bundle.test.ts`)
3. ทุก `Domain.xxx` ที่ไฟล์ `.gs` เรียก ต้องมีอยู่จริงใน bundle และทุกไฟล์ `.gs` ต้อง syntax ถูก
   (`appsscript-syntax.test.ts`) — ข้อนี้สำคัญเพราะ `.gs` เป็น JavaScript ล้วน TypeScript ช่วยไม่ได้

## ความปลอดภัยที่ปิดไว้แล้ว

| ช่องโหว่ | วิธีปิด |
|---|---|
| ปั่นสิทธิ์ตัวเองเป็น admin ผ่าน token | session token เซ็นด้วย HMAC-SHA256 และ**อ่านสิทธิ์จริงจากชีตทุกคำขอ** ไม่เชื่อค่าใน token |
| ถอนสิทธิ์แล้วไม่มีผลทันที | `tokenVersion` ในชีต — บวกหนึ่งแล้ว token ทุกใบของคนนั้นตายทันที ไม่ต้องรอหมดอายุ |
| แทรกสูตรลงชีต (`=IMPORTRANGE(...)` ในหัวข้อประชุม) ให้ทำงานตอนผู้ดูแลเปิดไฟล์ | บังคับทุกค่าที่เขียนลงชีตเป็นข้อความล้วน และอ่านกลับได้ค่าเดิม |
| ผู้ดูแลที่ถูกถอดถอน ล็อกอินกลับมาเป็น admin ใหม่ | สร้างผู้ดูแลคนแรกได้เฉพาะตอนที่ยังไม่มีผู้ดูแลในระบบเลย |
| token ปลอมถูกเดาด้วยการวัดเวลา | เทียบลายเซ็นแบบใช้เวลาคงที่ |
| ID token ของแอปอื่นถูกนำมาสวม | ตรวจ `aud` ว่าตรงกับ Client ID ของระบบ และ `email_verified` |

### ข้อจำกัดด้านความปลอดภัยที่ยังเหลือ (บอกตามจริง)

- **ไม่มีการจำกัดอัตราการเรียก `login`** — ถ้ามีคนรู้ URL แล้วยิงซ้ำ ๆ จะกินโควตา UrlFetch
  (20,000 ครั้ง/วัน) จนคนอื่นล็อกอินไม่ได้ ความเสี่ยงต่ำเพราะ URL ไม่เปิดเผย
  แต่ **ไม่ใช่ศูนย์** จะปิดช่องนี้ใน M7
- ความปลอดภัยทั้งหมดขึ้นกับ **การไม่แชร์ไฟล์ Sheets** ดูเหตุผลใน `docs/01-การติดตั้ง.md` ขั้นที่ 4
